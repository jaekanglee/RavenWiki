# 모바일 오프라인 보관함 실기 검증 절차

기기에서 확인할 것은 세 가닥이다. 비행기 모드로 쓴 글이 남는지, 재연결 때 스스로 올라가는지, 같은 문서를 PC와 동시에 고쳤을 때 무슨 일이 벌어지는지. 앞의 두 가닥은 unit test로 고정돼 있고(`DocumentRepositoryTest`), 세 번째는 **현재 코드로는 서버 충돌이 감지되지 않는다** — 아래 §3에서 그 이유와 관찰해야 할 실제 증상을 적었다.

## 준비

1. PC에서 API 기동: `raven api` (또는 `python -m raven.api`) — 기본 포트 8765
2. 앱 설치: `cd mobile && ./gradlew :androidApp:installDebug` (또는 `make deploy-dev`로 Firebase 배포본)
3. 앱 설정 탭에서 endpoint를 PC의 Tailscale IP로 지정, API Key 입력
4. 검증용 vault 선택 (스크래치 vault 권장 — `~/Raven/*` 실데이터에 쓰지 말 것)
5. PC 쪽에 관찰창 두 개 띄우기
   - `tail -f` 로 API 로그
   - `raven log list --vault <vault>` 로 write 기록

## §1 비행기 모드 작성 → 로컬 보존

| # | 조작 | 기대 |
|---|---|---|
| 1 | 문서 목록에서 아무 문서나 열어 본문이 보이는 것 확인 | 본문 표시 (fetchDocument 성공) |
| 2 | 비행기 모드 ON | — |
| 3 | 새 문서 작성(+ 버튼) → 제목·본문 입력 → 저장 | 저장이 **실패로 보이지 않고** 목록에 즉시 나타남 |
| 4 | 저장한 문서를 다시 열기 | 입력한 본문 그대로 |
| 5 | 앱 강제 종료(스와이프) → 재실행 → 같은 문서 열기 | 본문 유지 (SQLite Document 테이블에 있음) |
| 6 | PC에서 `raven log list` 확인 | 이 문서에 대한 write 기록 **없음** (아직 안 올라갔으니 정상) |

여기서 본문이 비면 outbox가 아니라 로컬 캐시 저장이 깨진 것 — `saveDocument`가 `insertDocument` + `enqueuePendingWrite`를 한 트랜잭션에서 하므로 둘 중 하나만 남을 수는 없다.

## §2 재연결 → 자동 전송

| # | 조작 | 기대 |
|---|---|---|
| 1 | 비행기 모드 OFF, 네트워크 복구 대기 | — |
| 2 | 목록 화면에서 아래로 당겨 새로고침 | 스피너 → 완료 |
| 3 | PC에서 파일 확인: `ls <vault>/content/` | §1에서 만든 slug의 `.md` 파일 존재 |
| 4 | `raven log list --vault <vault> \| head` | 방금 문서의 `create`/`update` 기록 |
| 5 | 앱에서 같은 문서 열기 | 본문 동일 (서버 왕복 후에도 안 깨짐) |
| 6 | 다시 당겨 새로고침 | 같은 문서가 **중복 전송되지 않음** (전송 성공 시 큐에서 제거됨) |

전송 트리거는 `syncDocuments`의 첫 줄 `flushPendingWrites()`다. 즉 **당겨 새로고침이 곧 재전송 시도**이고, 백그라운드 자동 재시도는 없다. 앱을 열지 않으면 올라가지 않는 것이 현재 설계다.

## §3 동시 수정 (현재 상태: 충돌 감지 없음)

`PendingWrite.failureKind`에 `CONFLICT`(HTTP 409/412) 분기가 있지만, 모바일 PUT은 `{"content": ...}`만 보내고 `precondition` 토큰을 보내지 않는다. 서버(`PUT /api/vaults/{name}/pages/{slug}`)는 precondition이 없으면 lost-update 검사를 건너뛰므로 **409가 나오지 않는다.** 따라서 이 절차의 목적은 "충돌이 잡히는지"가 아니라 **어느 쪽 글이 지워지는지 눈으로 확인**하는 것이다.

| # | 조작 | 기대(현재 코드) |
|---|---|---|
| 1 | 앱에서 문서 A 열기 (본문 캐시됨) | 본문 표시 |
| 2 | 비행기 모드 ON, 앱에서 A 본문 끝에 `모바일 추가` 저장 | 로컬 반영 + 큐 적립 |
| 3 | PC 대시보드에서 같은 A 본문 끝에 `PC 추가` 저장 | PC 저장 성공 |
| 4 | 앱 비행기 모드 OFF → 당겨 새로고침 | 앱의 PUT이 **성공**하고 A는 앱 본문으로 덮인다 → `PC 추가` 소실 |
| 5 | PC에서 A 파일 확인 | `모바일 추가`만 있고 `PC 추가` 없음 |
| 6 | `raven log list` | update 2건 (PC → 모바일 순) |

4~5에서 `PC 추가`가 사라지는 것을 확인했다면 그것이 지금의 정확한 동작이다. 이걸 막으려면 모바일이 `fetchDocument` 때 받은 precondition을 저장해 PUT에 실어야 하고(서버는 이미 응답에 준다), 그때 비로소 `failureKind=CONFLICT`가 채워져 앱에서 "서버가 먼저 바뀌었습니다" 안내를 띄울 수 있다. 별도 패치 대상.

## 실패했을 때 남길 것

- 어느 단계(§n-#m)에서 어긋났는지
- 앱 스낵바 문구 전문
- PC API 로그의 해당 요청 줄 (메서드/경로/상태코드)
- `raven log list --vault <vault> | head -20`

## 관련

- 큐 자체의 회귀 가드: `mobile/shared/src/androidUnitTest/.../DocumentRepositoryTest.kt`
  (`offlineSaveKeepsContentAndPendingWrite`, `reconnectFlushSendsPendingWriteAndClearsIt`,
  `pendingWritesOfDifferentVaultsDoNotCollide`, `failedRemoteWriteRecordsErrorAndConflictKind`)
- 서버 lost update 방어: `raven/api/server.py` `update_page` (precondition)
